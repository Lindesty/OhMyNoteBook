# 07 - 并发集合的良好与不良实践

## 概述

本模块聚焦于并发集合（特别是 ConcurrentDictionary）的正确使用方式，探讨如何在保证线程安全的同时获得良好的性能。通过基准测试对比，我们将揭示并发集合使用中的常见误区和最佳实践。

使用并发集合的目的是让多线程访问数据更加安全高效。但如果使用不当，不仅无法获得性能提升，反而可能导致性能下降。本模块将帮助你理解：
- 何时以及如何使用并发集合才能获得最佳效果
- 哪些操作在并发集合上是昂贵的
- 如何设计代码以正确处理并发集合的状态

## 核心概念

### 1. 为什么关注性能？

使用并发集合的根本原因是为了支持多线程访问数据，而使用多线程的主要目的是提高应用程序的性能和响应能力。

然而，并发编程带来了诸多挑战：
- 需要仔细考虑线程同步逻辑
- 可能出现微妙的竞态条件和数据损坏问题
- 代码复杂度显著增加

如果使用并发集合后性能反而下降，那么所有的付出都将白费。因此，理解并发集合的性能特性至关重要。

### 2. 基准测试设计

为了深入理解并发集合的性能特性，我们设计了一个基准测试程序，比较以下三种场景：

1. **单线程 + 普通 Dictionary**：基准参考
2. **单线程 + ConcurrentDictionary**：评估并发字典的额外开销
3. **多线程 + ConcurrentDictionary**：评估并发访问的真实性能

测试方法包括：
- **Populate（填充）**：创建并填充大型字典
- **Enumerate（枚举）**：遍历字典并累加所有值
- **Lookup（查找）**：通过键逐个查找元素

#### 单线程基准测试类

```csharp
class SingleThreadBenchmark
{
    static void Populate(IDictionary<int, int> dict, int dictSize)
    {
        for (int i = 0; i < dictSize; i++)
        {
            dict.Add(i, 1);
        }
    }
    
    static int Enumerate(IDictionary<int, int> dict)
    {
        int total = 0;
        foreach (var keyValPair in dict)
        {
            total += keyValPair.Value;
        }
        return total;
    }
    
    static int Lookup(IDictionary<int, int> dict)
    {
        int total = 0;
        int count = dict.Count;  // 缓存 Count 属性
        for(int i = 0; i < count; i++)
        {
            total += dict[i];
        }
        return total;
    }
}
```

**注意**：使用 `IDictionary<int, int>` 接口引用，这样可以将普通 Dictionary 或 ConcurrentDictionary 作为参数传入。ConcurrentDictionary 虽然没有公开的 Add 方法，但它显式实现了 IDictionary 接口的 Add 方法，可以通过接口引用调用。

#### 多线程基准测试类

```csharp
class ParallelBenchmark
{
    static void Populate(ConcurrentDictionary<int, int> dict, int dictSize)
    {
        Parallel.For(0, dictSize, (i) =>
        {
            dict.TryAdd(i, 1);
        });
    }
    
    static int Enumerate(ConcurrentDictionary<int, int> dict)
    {
        int total = 0;
        Parallel.ForEach(dict, keyValPair =>
        {
            Interlocked.Add(ref total, keyValPair.Value);
        });
        return total;
    }
    
    static int Lookup(ConcurrentDictionary<int, int> dict)
    {
        int total = 0;
        Parallel.For(0, dict.Count, (int i) =>
        {
            Interlocked.Add(ref total, dict[i]);
        });
        return total;
    }
}
```

**注意**：
- 使用 `Parallel.For` 和 `Parallel.ForEach` 实现多线程操作
- 使用 `Interlocked.Add` 确保累加操作的线程安全
- 直接使用 `ConcurrentDictionary<int, int>` 而非接口，因为普通 Dictionary 无法支持多线程操作

### 3. 不良实践：过度访问共享状态

#### 初始基准测试结果

运行基准测试后，结果令人惊讶：

| 操作 | Dictionary (单线程) | ConcurrentDictionary (单线程) | ConcurrentDictionary (多线程) |
|------|---------------------|-------------------------------|-------------------------------|
| Build | 9 ms | 37 ms | 较慢 |
| Enumerate | 较快 | 较慢 | 最慢 |
| Lookup | 2 ms | 较慢 | 6 ms |

**问题发现**：
1. ConcurrentDictionary 在单线程环境下明显比普通 Dictionary 慢（构建操作慢约4倍）
2. 多线程版本不仅没有带来性能提升，反而更慢

#### 原因分析

问题根源在于代码设计方式。观察 `Populate` 方法的并行版本：

```csharp
// 不良实践示例
Parallel.For(0, dictSize, (i) =>
{
    dict.TryAdd(i, 1);  // 仅此一行，没有其他本地工作
});
```

每个线程迭代的工作仅仅是向字典添加一个条目，**没有任何不涉及共享状态的本地计算**。这意味着：
- 线程几乎将所有时间都花在访问共享状态上
- 大量的线程同步开销
- 并发带来的好处被同步开销完全抵消

这**不是**正确的多线程编程方式。

### 4. 良好实践：减少共享状态访问

#### 改进方法

正确的做法是让每个线程在访问共享集合之间，先完成一些只使用本地数据的工作：

```csharp
// Worker 类 - 模拟本地计算
public static class Worker
{
    public static int DoSomething()
    {
        int total = 0;
        for (int i = 0; i < 1000; i++)
            total += i;
        return total;
    }
}

// 改进后的并行操作
static void Populate(ConcurrentDictionary<int, int> dict, int dictSize)
{
    Parallel.For(0, dictSize, (i) =>
    {
        dict.TryAdd(i, 1);
        Worker.DoSomething();  // 添加本地计算
    });
}

static int Enumerate(ConcurrentDictionary<int, int> dict)
{
    int total = 0;
    Parallel.ForEach(dict, keyValPair =>
    {
        Interlocked.Add(ref total, keyValPair.Value);
        Worker.DoSomething();  // 添加本地计算
    });
    return total;
}

static int Lookup(ConcurrentDictionary<int, int> dict)
{
    int total = 0;
    Parallel.For(0, dict.Count, (int i) =>
    {
        Interlocked.Add(ref total, dict[i]);
        Worker.DoSomething();  // 添加本地计算
    });
    return total;
}
```

#### 改进后的结果

改进后，ConcurrentDictionary 在多线程环境下显著优于单线程的普通 Dictionary：

| 操作 | Dictionary (单线程) | ConcurrentDictionary (多线程) |
|------|---------------------|-------------------------------|
| Enumerate | 较慢 | **显著更快** |
| Lookup | 较慢 | **显著更快** |
| Build | 基准 | 性能相当 |

#### 核心原则

> 如果想从并发集合获得性能优势，必须确保访问集合的时间只占每个线程工作的一小部分。这样，并发带来的收益才能远超线程同步的开销。

### 5. Count 属性的性能陷阱

#### 问题发现

修改代码，在循环中不缓存 Count 属性：

```csharp
// 不良实践：每次迭代都访问 Count
static int Lookup(IDictionary<int, int> dict)
{
    int total = 0;
    for(int i = 0; i < dict.Count; i++)  // 每次迭代都调用 Count
    {
        total += dict[i];
    }
    return total;
}
```

测试结果显示：
- **普通 Dictionary**：性能影响微乎其微
- **ConcurrentDictionary**：并行查找从 16ms 暴涨到近 3 秒（慢约150倍！）

#### 原因分析

为什么 `ConcurrentDictionary.Count` 如此昂贵？

1. **聚合状态的概念**：Count 属性询问的是整个字典的整体状态，它依赖于集合中的每一个元素。

2. **并发环境下的复杂性**：
   - 并发集合设计为支持多个线程持续修改数据
   - 很难确定"当前状态"是什么
   - 需要知道其他线程是否正在修改数据
   - 可能需要同步大量线程

3. **对比普通集合**：
   - 普通 Dictionary 的 Count 只是访问一个内部字段
   - 几乎零成本

#### 其他昂贵的聚合状态操作

除了 Count，以下操作同样昂贵：
- `IsEmpty` 属性
- `Keys` 属性（获取所有键）
- `Values` 属性（获取所有值）
- `ToArray()` 方法（复制整个字典到数组）

> **最佳实践**：尽量避免频繁查询并发集合的聚合状态。

### 6. 状态管理的最佳实践

#### 回顾课程中的模式

在本课程的前面部分，我们已经遇到过类似的问题：

```csharp
// 不良实践：假设集合处于特定状态
var value = dict[key];      // 索引器假设键存在
dict.Remove(key);           // Remove 假设键存在

// 良好实践：不假设状态，使用 Try 方法
dict.TryGetValue(key, out value);  // 不假设键存在
dict.TryRemove(key, out value);      // 不假设键存在
```

#### 两条核心原则

**原则一：避免假设集合处于特定状态的方法**

| 避免 | 推荐 |
|------|------|
| `Add()` | `TryAdd()` |
| `dict[key]`（获取） | `TryGetValue()` |
| `Remove()` | `TryRemove()` |
| `Dequeue()` | `TryDequeue()` |

原因：在并发环境中，关于集合的任何信息都可能立即过时。

**原则二：避免频繁查询聚合状态**

- 尽量不要频繁调用 `Count`、`IsEmpty`、`Keys`、`Values`、`ToArray()`
- 这对 ConcurrentDictionary 和 ConcurrentBag 影响最大
- ConcurrentQueue 和 ConcurrentStack 由于内部数据结构的特性，影响相对较小

#### 统一的指导思想

这两条原则反映了同一个核心理念：

> **当多个线程操作一个集合时，尽量将并发集合视为一个"流动的"对象，在其上执行操作，而不是将其视为处于某种确定状态的对象。**

集合的状态是不断变化的，你的代码不应该依赖某个特定的"快照"状态。

## 要点总结

### 性能相关

1. **并发集合有开销**
   - ConcurrentDictionary 在单线程环境下比普通 Dictionary 慢
   - 这是因为内部需要维护线程同步机制
   - 只有在真正的多线程场景下才能体现价值

2. **访问共享状态需要谨慎**
   - 如果每个线程大部分时间都在访问共享状态，性能会很差
   - 应该让线程主要处理本地数据，偶尔访问共享集合
   - 本地计算占比越高，并发优势越明显

3. **聚合状态操作代价高昂**
   - Count、IsEmpty、Keys、Values、ToArray() 等操作很昂贵
   - 应该尽量减少这类操作的调用频率
   - 在循环条件中避免使用 Count，应预先缓存

### 设计原则

1. **使用 Try 系列方法**
   - 不假设集合状态
   - 使用 TryAdd、TryGetValue、TryRemove 等

2. **最小化共享状态访问**
   - 将大部分工作放在本地计算
   - 只在必要时才与共享集合交互

3. **正确认识并发集合**
   - 视其为流动的对象
   - 在其上执行操作而非查询状态
   - 接受状态可能随时变化的事实

### 警告

基准测试是一门不精确的科学，结果可能受多种因素影响。本模块的测试仅用于说明不同使用模式对性能的大致影响，不应作为精确的性能数据参考。
